# Storage audit remediation: local safety boundaries

## Decisions and evidence

This is a local single-client containment, not a durable synchronization protocol or an operational accounting sign-off. Existing state and earlier uncommitted edits were preserved.

- Startup distinguishes unreadable local/server data from an empty facility, hydrates collections even when no facility is present, and blocks automatic writes if local and server states diverge. Neither divergent copy is automatically removed or replaced.
- A session that starts offline stays on its local branch. If a server POST fails or its acknowledgement is ambiguous, subsequent session writes also remain local; recovery requires a fresh comparison rather than automatic overwrite. The UI reports whether changes are browser-only, or that the latest state could not be saved. It does not claim synchronization.
- Client writes are serialized in invocation order. A later queued write waits for the earlier result, including an offline fallback. If local storage rejects the write, the failure is returned and the in-memory page remains available to the user. The client does not silently clear an existing local copy after a successful server save; a later difference may require review.
- Unsupported per-unit billing quantities and revenue-share amounts fail closed instead of assuming a count or turnover. Termination proration uses the actual month length, multi-month billing periods count months accurately, and initial billing is evaluated before changing allocation. Per-lease intended-use fields are separate from the tenant record and default to unknown. Contract-specific policy still requires owner/accountant review.

## Verification

Before the storage changes, three focused regressions failed: offline saves retried the server, a rejected local save was silently ignored, and simultaneous saves started out of order. Afterward, `npm test -- --run tests/auditStorageRecovery.test.ts tests/auditBillingBoundaries.test.ts` passed 13 tests; `npm test` passed 118 tests in 15 files; `npm run typecheck` and `git diff --check` passed. This is automated local T2/S2 evidence, not browser, multi-client, real-provider, accounting, or production acceptance. Tests use mocked storage and network, not operating records.

## Remaining work and decisions

- The earlier no-queue/no-revision finding was partially addressed by the follow-up below. Multiple independent server processes or out-of-band edits to the store remain outside its single-instance queue and require a real interprocess storage/locking design.
- Reset now waits for prior saves and rejects new saves while in flight, but the UI does not disable every editing control while a reset request is pending. Review the behavior of concurrent edits and provide an explicit recovery workflow; do not use reset to resolve a conflict.
- The offline outbox is separate from this full-state path. Determine canonical event, transaction, retry and audit ownership before integrating it. A local `events` array is not an atomic, tamper-evident transaction log.
- Local/server comparison is currently whole-object `JSON.stringify` equality, so harmless ordering differences may require review. No user-facing compare, export, or conflict resolution workflow has been validated. A previously matching local copy may become stale following a successful server save and cause a conservative conflict on restart.
- P06 spatial facility/space IDs and P09 landlord facility/space IDs have no verified shared mapping or authorization contract. Determine physical ownership, tenancy and custody boundaries before sharing data.
- Browser reload/recovery, actual disk-full behavior, receipt/payment and meter reconciliation, lease lifecycle, accounting policy, and end-user acceptance remain open.

## Conditional-write and reset follow-up

The local server accepts `GET /data` with an ETag and requires the matching `If-Match` for POST and DELETE. Mutations serialize inside one service instance and commit through the existing temporary-file/rename sequence before acknowledgment. A legacy schema-1 file without revision metadata remains readable; on its next successful write, `storageRevision` is added. Each committed write receives a fresh identifier persisted with the file, so changing A to B and back to A does not make the original A revision valid again. Requests without a precondition get HTTP 428 and stale revisions get 412. Older clients that do not send `If-Match` cannot write to the updated service; the new client reads older servers without conditional writes but keeps its edits in browser storage. No unattended synchronization or migration is implied.

Fields present in an existing store that the current service does not model are carried forward on ordinary saves. If such fields exist, reset returns 409 rather than reporting a complete clear or deleting unknown work. The old plural `facilities` migration still exposes only its first entry to the current client; additional original entries are retained in the unrecognized legacy field and need explicit migration/review. A failed or ambiguous server reset preserves the browser copy and blocks further writes until review. New saves are rejected while reset is pending; prior queued saves finish before it begins. Reset warnings are also shown in persistent storage status.

Regression evidence: the storage-service integration test first reproduced the repeated-content revision flaw and loss of an unknown legacy field; it now passes **2 tests** using temporary stores and loopback ephemeral ports, including competing writes, stale delete, restart and CORS checks. The client recovery tests first reproduced ambiguous reset removing the local copy and a new save recreating data after reset; all **14 focused tests** now pass. Full P09 `npm test` passed **124 tests across 15 files**; `npm run typecheck` and scoped `git diff --check` passed. This is local automated T2/S2 evidence. No existing store was reset, no customer data was transmitted, and real browser, cross-process, filesystem-failure and user recovery acceptance remain unverified. The outbox and audit-event transaction guarantees remain separate work.

## Payment, event and consumption follow-up

New payments retain date, user-entered source, received/applied/overpaid amounts, a generated transaction identifier and, when issued, the receipt number in the ledger entry. When details begin on an existing entry, the prior applied and overpaid totals are retained as opening balances rather than fabricated transactions. Invalid or zero payment values are rejected. The UI prepares payment and receipt against a copy of the ledger entry rather than mutating the currently rendered entry first. A partial receipt does not set a fully-paid date; analytics also excludes legacy partial entries with such a date from paid-entry counts. This does not reconstruct past payments or authenticate actual receipt of money. Receipt identifiers are still also maintained in a separate list, and transaction idempotency, atomic audit events, authenticated actors, adjustments, refunds and accounting policy remain unresolved.

The unused-by-UI event factory now defaults to `reported` and `Not supplied` for actor rather than inventing an observed event or operator. This changes the additive event status vocabulary while retaining old explicit values. Events remain locally stored records with no append-only, transaction, identity or publication guarantee. Existing events are not rewritten or upgraded.

New meter entries explicitly represent kWh consumed within a start/end period, not cumulative meter registers. Same-space overlapping periods are rejected because this model does not distinguish multiple meters for one space. Undated legacy records stay visible with unknown periods and are excluded from bill allocation. Allocation requires an exact period match, valid finite data, nonzero consumption and a bill amount in whole paise; it rejects overlapping records and distributes rounding remainders deterministically so displayed allocations add to the bill. The allocation is a preview, not a posted charge; it covers only the included readings and cannot establish that all relevant meters are present. The displayed tariff is an example. Meter identity, cumulative readings, shared/common-area or fixed charges, tariff selection, approved allocation policy and real-user validation remain open.

Before the fix, tests reproduced partial receipt dates, missing transaction history, acceptance of NaN/infinite/zero payments, and loss of one paise in a three-way split. Afterward the full P09 suite passed **134 tests across 17 files**, `npm run typecheck` passed and scoped `git diff --check` passed. The meter test was first run against a missing new helper, so that initial failure established missing implementation rather than reproducing the prior UI's mixed-period behavior. These are local automated T2/S2 checks, not browser, accounting, actual payment, or device evidence.

## Follow-up: schema, payment and concurrent recovery boundaries

The client accepts only schema version 1 and fails closed on missing, unsupported or unreadable formats. It does not migrate or overwrite them. Same-version top-level fields that this client does not own are carried forward into offline saves; reset refuses to remove a local copy with such fields. Unknown server-side fields continue to be retained by the service. No unknown fields are interpreted as current data or silently removed.

The client compares browser storage with the exact value last read or written by this session before saving or resetting. It checks again after a server save and after a server reset, because another tab can change the local copy while a request is pending. When a changed copy is observed, it blocks further writes and preserves the local copy and in-memory state for review. A server request may already have succeeded; the message distinguishes that possibility or an acknowledged reset from a wholly local outcome. These checks detect conflicts at observation points and are **not an atomic compare-and-swap across tabs**. The server's queue is likewise per service instance, not an interprocess lock. Both cases need an authoritative synchronization design before claiming multi-client safety.

Payment conversion now rejects values and existing balances that cannot be represented as safe integer paise before changing a ledger entry. Ledger entries and receipt identifiers are updated together through one financial state transition. A pending-action guard avoids duplicate clicks until the ledger update renders. The application disables its editable shell with `inert` while a reset is pending, and payment actions also check the reset guard. The payment date defaults to the browser-local calendar day and is editable; current overdue and aging views derive status from the current balance and selected day rather than trusting a stale stored label. These are not reconstruction of historical balances or an authenticated accounting workflow.

The targeted storage tests reproduced and then passed preservation cases for unknown fields, offline local changes, a local copy appearing before server save, a change during an in-flight save, and a change during an in-flight server reset. The full `npm test` passed **151 tests across 19 files**, `npm run typecheck` passed, the isolated storage-server suite passed **2 tests**, and scoped `git diff --check` passed. S2 applies to the new reproduced storage regressions; the full suite is T2/S1. Tests use mocked browser storage or disposable loopback stores. An earlier isolated synthetic browser run reproduced rapid duplicate payment actions before the financial-state change; the final browser payment/reset flows have not yet been reverified. Unknown record migration, conflict comparison/recovery UI, atomic authenticated event logging, receipt idempotency and actual accounting review remain open.

The shared INR formatter formerly rounded fractional rupees to whole rupees and displayed non-finite numbers as zero. It now displays fractional values to two decimal places and invalid values as unknown (`—`), retaining Indian digit grouping and the explicitly requested compact mode. `tests/format.test.ts` reproduced the missing-paise output before the change; the focused formatting and date/status tests passed 10/10 afterward and typecheck passed. This fixes presentation, not the separate tariff, tax, receipt or accounting decisions.
